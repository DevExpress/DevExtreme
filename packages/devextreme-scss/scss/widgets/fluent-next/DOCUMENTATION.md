# DOCUMENTATION.md — что должно войти в публичную документацию темы fluent-next

Это ТЗ на пользовательскую документацию кастомизации (не сама дока). Аудитория будущей доки —
пользователь DevExtreme, который хочет перекрасить/подстроить тему, не зная её внутренностей.
Внутренние доки (NAMING, DIVERGENCES, …) сюда не переезжают.

Сверка с DevExpress Blazor выполнена 06.08.2026 по живому CSS демо-сайта (26.1.4) и официальным
докам — их модель проверена и взята за ориентир там, где помечено «как у Blazor».

## 1. Контракт кастомизации — первая страница доки

Одна таблица и две фразы, без теории:

| Слой | Префикс | Обещание |
|---|---|---|
| Дизайн-токены: роли и шкалы | `--dxds-*` | **Публичное API.** Стабильны, меняются только мажорами пакета токенов. Кастомизируйте через них |
| Компонентные переменные | `--dx-*` | Эволюционируют между версиями (переименования — через ченджлог). Для точечной подстройки; «навсегда» не обещаются |
| SCSS-переменные | `$…` | Внутренности сборки. В публичную доку не выносятся вообще |

Формулировка обещания — дословно как у Blazor («Use public `--dxds-*` variables only… may change
between versions»): проверено, что оба продукта шипят **один и тот же** пакет `--dxds-*`
(в их демо-CSS — те же `--dxds-color-bg-primary-subtle`, `--dxds-primary-10…170`) —
это надо прямо продать в доке как кросс-продуктовое единообразие.

## 2. Три рецепта кастомизации (по нарастающей адресности)

Каждый — работающий сниппет + скриншот до/после. Все четыре работают с 13.08.2026 (№4 — на
пилотных компонентах; полнота растёт с волной массового потребления).

1. **Глобальная перекраска ролями** — переопределение `--dxds-color-*` в `:root`:
   ```css
   :root { --dxds-color-bg-primary: #b06ab3; }
   ```
2. **Свой акцент файлом палитры** (аналог Blazor `FluentPrimary.css`): один CSS-файл с 17 ступенями
   `--dxds-primary-10…170` в `:root`. У нас ступени генерятся пайплайном (`accents/*`) — в доку
   идёт готовый шаблон файла.
3. **Скоуп-кастомизация на контейнере** — главный рецепт Blazor-доки, работает и у нас, потому что
   правила читают `var(--dxds-…)`:
   ```css
   .my-sidebar { --dxds-color-bg: #f6f2ff; }
   ```
4. **Адресные компонентные ручки** `--dx-<component>-<slot>[-<state>]` (покой — без суффикса) — **работает по всей теме
   с волн F5–F9 (13.08.2026)**: ~1050 чтений тира в правилах (декларации, аргументы миксинов,
   интерполяции в calc, значения with()-проводки в base); вне тира осталось 24 математически
   связанных мест (ратчет `unconsumedManifestReads`) — в них пер-инстансная кастомизация не
   течёт, честно перечислить в доке. Проверено живыми смоуками (кнопка, тост-чейн, сплиттер
   сквозь base-инъекцию):
   ```css
   .dx-splitter { --dx-splitter-resize-handle-bg-hovered: tomato; }
   ```
   Правила каскада, которые дока обязана проговорить: переменная объявлена на корне компонента,
   поэтому пользовательский оверрайд должен попасть НА тот же элемент (класс инстанса, инлайн
   `style.setProperty`) либо быть селектором той же специфичности в стайлшите ПОСЛЕ темы;
   оверрайд на контейнере-предке компонентную переменную не перебьёт (это отличие от `--dxds-*`,
   которые объявлены в `:root` и скоупятся контейнером). Генерические имена тянут вариантные через
   эмитированные чейны: оверрайд `--dx-toast-bg` на инстансе перекрашивает и info-тост
   (`--dx-toast-info-bg: var(--dx-toast-bg)`).

## 3. Справочники — генерировать, не писать руками

- **Таблица ролей** `--dxds-color-*` (light/dark значения) — генерируется из пакета токенов
  (машинерия уже есть: резолвер из `tools/review/evidence.mjs`).
- **Таблица шкал** (spacing/radius/font/line-height/opacity) — оттуда же.
- **Манифест `--dx-*`** — собирается сканом сгенерированных `<folder>/_public.scss` и рукописных
  `<folder>/_public-links.scss` (2231 имя на 06.09.2026; проекции пишет `tools/naming/publish.mjs`
  по правилам `tools/naming/tier.ts`), группировка по компонентам, колонки
  «имя / что красит / значение по умолчанию».
- **Акцентная палитра**: 17 ступеней + шаблон файла.

Правило: справочная страница без генератора протухает за релиз — в доку попадает только то, что
собирается из репо командой.

## 4. Тёмная тема и размерные моды

- Как подключаются бандлы `dx.fluent-next.blue.{light,dark}[.compact].css`. Размерная мода — это
  выбор файла. Режим — уже нет: **каждая сборка несёт оба режима**, класс выбирает между ними
  (см. §4.1). Файл задаёт, какой режим действует по умолчанию.
- Все роли режим-зависимы: пользовательский оверрайд ролей в `:root` перекрывает ОБА режима —
  показать паттерн разделения (`:root` + класс режима).

### 4.1. Режим классом — рецепт для доки

Три класса, публичный контракт (см. NAMING.md):

| Класс | Что означает |
|---|---|
| `dx-theme-mode-light` | светлый режим на этом элементе и внутри него |
| `dx-theme-mode-dark` | тёмный режим на этом элементе и внутри него |
| `dx-theme-mode-inverted` | режим, противоположный окружению |

**Страница целиком** — класс на `<html>`:

```html
<html class="dx-theme-mode-dark">
```

Именно на `<html>`, а не на `<body>` или на обёртке: это тот же элемент, на котором объявлен
`:root`, поэтому существующие переопределения ролей на `:root` продолжают работать как раньше.
Класс на элементе внутри страницы перекрыл бы для всего содержимого значения, унаследованные от
`:root`, — включая пользовательские. Переключение — это добавление и снятие класса; файл стилей
не перезагружается.

**Отдельный блок** — класс на самом блоке:

```html
<div class="dx-theme-mode-dark">…</div>
<div class="dx-theme-mode-inverted">…</div>
```

Переопределения ролей для такого блока делаются **на том же элементе, что несёт класс**, либо в
таблице стилей, подключённой после темы. Правило одно на всю тему: `:root` и классы режима имеют
равный вес, спор решает порядок подключения.

Две оговорки, которые дока обязана проговорить:

- **«Инвертированный» — про ближайшее окружение, и он рекурсивен.** Он переворачивает режим
  ближайшего окружающего блока, а не режим сборки; инвертированный блок внутри
  инвертированного переворачивается обратно. Работает на любой глубине.
- **Не всё идёт за классом.** Иконки, у которых цвет запечён в data-uri (diagram, gantt,
  fileManager, list, timeView), и маркер темы сохраняют вид режима сборки. Перечислить — это
  тот же список, что и в §5 про иконки. Отдельно: графики и прочая визуализация берут тему
  со стороны скриптов, по маркеру загруженного файла, поэтому классу режима не следуют.
- **Своё переопределение роли тоже разрешается там, где объявлено.** Если пользователь объявил
  `:root { --my-brand: … }` и подставил его в роль, значение внутри блока с классом режима
  останется тем, что вычислилось на корне. Рецепт тот же, что у темы: повторить объявление на
  классах режима, либо (проще) переопределять роли на том же элементе, что несёт класс.

Продукт **не** зеркалит текущий режим на `<html>` сам: класс ставит приложение.

## 5. Ограничения и антипаттерны — честная страница

- **Иконки в data-uri не кастомизируются переменными**: `var()` внутри встроенного SVG не
  резолвится (рендер чёрным). Перечислить затронутые места (radio-button, чекбоксы гридов,
  часы timeView, иконки gantt/diagram/fileManager) и штатный обход (CSS `filter`/замена иконки).
- **Опечатка в имени переменной = молча сломанный стиль**: invalid-at-computed-value-time
  откатывает к `unset`, а не к предыдущему значению каскада. Рекомендовать проверку в DevTools.
- Не полагаться на `--dxds-<палитра>-<ступень>` компонентных токенов DS (уходят из бандла) и на
  что-либо с префиксом `$`.
- RTL: какие переменные физические по построению (задокументировать точечно).

### 5.1. Шесть `--dx-*`, которые ставит сам компонент — не ручки настройки

Есть переменные с префиксом `--dx-`, которые выглядят как компонентный тир, но им не являются:
их **записывает JavaScript во время работы**, а читает общий слой стилей. Пользователь их
переопределять не должен: при следующей отрисовке значение будет перезаписано, а у CardView
вдобавок сломается раскладка сетки. В доке им нужен отдельный блок с явной формулировкой
«это не точка кастомизации».

Полный список — шесть имён, одинаковых во всех четырёх темах (живут в `base/**`, не в теме):

| переменная | ставит | что задаёт | фолбэк | если рантайм значения не дал |
|---|---|---|---|---|
| `--dx-cardview-cardsperrow` | `card_view/content_view/content/content.tsx` | число колонок сетки карточек | нет | объявление исчезает; рантайм всегда даёт число (дефолт 3, `auto` считается в `view.tsx`) |
| `--dx-cardview-card-min-width` | там же | минимальная ширина карточки | `$cardview-card-min-width` | действует минимум темы |
| `--dx-cardview-card-max-width` | там же | максимальная ширина карточки | нет | объявление исчезает, `max-width: none` |
| `--dx-cardview-card-cover-max-height` | там же | высота обложки | нет | дефолт темы объявлен на контейнере карточек, рантайм его переопределяет |
| `--dx-cardview-card-cover-ratio` | там же | пропорции обложки | нет | объявление исчезает, обложка держит свои пропорции |
| `--dx-scheduler-animation-top` | `scheduler/appointment_popup/form.ts` | стартовая точка анимации попапа | `0` | анимация от верхней кромки |

**Правило фолбэков — записать явно, иначе читается как недосмотр:** у четырёх из шести фолбэка
нет **намеренно**. Если JS значения не дал (например, у обложки карточки не задан `ratio`),
объявление обязано исчезнуть целиком, а не подставить произвольное число: `aspect-ratio` с
выдуманным значением исказит картинку сильнее, чем его отсутствие.

**Механика, чтобы это не разъехалось:**

- список из шести имён существует машинно - `tools/naming/runtime-contract.json` (имя, сеттер,
  файл чтения, свойство, форма фолбэка, поведение без значения); по нему проверки поверхности в
  `tests/fluent-next-naming.test.ts` исключают эти имена, а `tests/fallback-policy.test.ts` держит
  форму каждого чтения в `base/**` и наличие сеттера в JS;
- генератор справочника `--dx-*` (см. §3) обязан читать список **оттуда** и вычитать эти имена
  из манифеста. Иначе они попадут в публичный справочник наравне с настоящими ручками — ровно та
  ошибка, которую этот раздел предотвращает;
- дублировать список прозой в доке нельзя: он должен приезжать из репозитория.

**Написание `--dx-cardview-cardsperrow` — решено 27.08.2026: оставляем как есть, переименования
не будет.** Имя написано слитно и грамматике имён темы не соответствует, но переменная не наша:
она приехала вместе с самим CardView и шипится клиентам минимум с 25.2.2 (проверено по собранным
`dx.all.js`), владелец — команда гридов. Это контракт отгруженного компонента, менять его ради
косметики имени не будем. Вопрос закрыт; в доке имя приводится как есть.

## 6. Эволюция `--dx-*` — правила игры

- Каждое переименование/удаление — строка в ченджлоге релиза с парой «старое → новое».
- Мажор может менять состав; минор — только добавлять.
- Рекомендация пользователю: массовую кастомизацию строить на `--dxds-*`, `--dx-*` — для точечной.

|---|---|---|
| Где объявлены публичные `--dxds-*` | `:root` (mode-файл: 1320 деклараций; accent-файл: 127) | `:root`, так же |
| Где объявлены компонентные | **НЕ в `:root`**: 8561 из 8585 `--dxbl-*` — на селекторах компонентов (`.dxbl-btn` 308, `.dxbl-calendar` 234, …), в `:root` только 24 | **как у Blazor с первого среза (13.08.2026)**: на корнях из `registries.rootSelectors`, 769 имён × корни = 1268 пар |

| Имена | 4935 уникальных; бутстраповские: аббревиатуры (`btn`, `fl`), состояние префиксом (`hover-bg`, `active-color`), физические оси (`padding-x/y`) | 768; полнословная грамматика: анатомия + слот + состояние суффиксом (`-bg-hovered`), логические оси |

**Рекомендация реализована волной F (13.08.2026):** `--dx-*` эмитятся **на корневом классе
компонента** (`.dx-splitter { --dx-splitter-…: …; }`) — (а) пер-инстансные оверрайды работают
(живой смоук), (б) `:root` не растёт, (в) рецепт №4 полноценен на пилотах. Тонкость, которой не
было в плане: у оверлеев корень — класс ОБЁРТКИ (`.dx-toast-wrapper`), потому что контент
рендерится вне исходного элемента; полный реестр — `registries.rootSelectors`.

## 8. Что НЕ включать в публичную доку

- Внутренние доки темы (NAMING/DIVERGENCES/…) и любые `$`-переменные.
- Компонентные токены DS (`--dxds-<component>-*`) — **не эмитятся** (исключены пайплайн-PR #34701, `50cd66a07f`; проверено по бандлу 13.08: ноль деклараций).
- Механику base/инъекций, байт-гейты, ратчеты — это контрибьюторское (внутренний README).
- Шесть переменных контракта JS → CSS **не включать в справочник ручек** — им место в разделе
  ограничений (§5.1) с формулировкой «ставит компонент, переопределять нельзя».
